## fork: сделать копию процесса

`fork()` — это единственный в Unix способ создать новый процесс. Он не запускает программу с нуля, а раздваивает текущую: создаёт почти точную копию вызвавшего процесса — потомка. Потомку достаётся копия всего окружения родителя: адресного пространства (кода, данных, кучи, стека), открытых файлов, текущего каталога. Логически это снимок родителя в момент вызова; физически память копируется лениво, но для программиста важно одно — с этого момента у процессов раздельные копии, и запись одного не видна другому.

Главная странность, из-за которой fork поначалу и не укладывается в голове: он **возвращается дважды**. Один раз — в родителе, второй — в свежесозданном потомке, и оба продолжают выполнять один и тот же код с одной и той же строки, следующей за `fork()`. Различить, где ты находишься, можно только по возвращённому значению: потомку `fork()` возвращает `0`, родителю — pid потомка (положительное число), а при ошибке возвращает `-1` в родителе, и никакого потомка не появляется. На этом значении и строится развилка: две ветки `if` — это код родителя и код потомка.

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("before fork\n");
    pid_t pid = fork();

    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        printf("child pid: %d\n", getpid());
    } else {
        printf("parent: my child has pid %d\n", pid);
    }
    return 0;
}
```

Строчки после `fork()` выполняют оба процесса; печатается и ветка потомка, и ветка родителя, потому что после вызова их уже двое. А вот в каком порядке они станут выполняться — не определено: планировщик может запустить первым любого из них. Это первое проявление правила, которое будет преследовать нас весь курс: **порядок выполнения параллельных сущностей не гарантирован**, и опираться на него нельзя.

У каждого процесса есть числовой идентификатор — pid. Свой процесс узнаёт его вызовом `getpid()`, а pid своего родителя — вызовом `getppid()`. Родителю pid потомка и так возвращает `fork`, а вот потомку, чтобы узнать себя, нужен именно `getpid()` — поэтому в примере выше потомок печатает свой pid через него, а не через возвращённое значение (у потомка оно равно нулю).

## wait и exit: собрать потомка

Потомок рано или поздно завершается — вызовом `exit(код)` или просто дойдя до конца функции `main`. Но исчезает он не сразу. Ядро придерживает о нём минимальную запись — прежде всего код возврата, до тех пор, пока родитель этот код не считает. Получает он его вызовом `wait()`: тот блокирует родителя, пока какой-нибудь его потомок не завершится, после чего возвращает pid завершившегося и через переданный указатель — статус завершения.

Смысл этой пары — не только дождаться, но и очистить информацию о потомке. Завершившийся процесс, чей код ещё не забрали через `wait`, называется зомби: программы уже нет, а запись в таблице процессов висит. Один-два зомби безобидны, но если они будут создаваться в больших количествах, то могут занять все возможные слоты с номерами pid. 

Когда потомков несколько, удобнее использовать системный вызов `waitpid`: он умеет ждать конкретного потомка по pid и принимает флаги (например, `WNOHANG` — «проверить, но не блокироваться»). Статус, который заполняет `wait`/`waitpid`, — не просто код: в него упакованы и способ завершения (сам вышел или убит сигналом), и, если сам, — код возврата. Распаковывают его макросами: `WIFEXITED(st)` отвечает, завершился ли потомок нормально, а `WEXITSTATUS(st)` достаёт из статуса те самые 0–255, что потомок отдал в `exit`.

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        exit(42);                     // потомок завершается кодом 42
    }
    int status;
    waitpid(pid, &status, 0);          // родитель собирает его
    if (WIFEXITED(status))
        printf("child exit with code %d\n", WEXITSTATUS(status));
    return 0;
}
```

## exec: заменить программу внутри процесса

`fork()` порождает копию *той же* программы. Чтобы процесс начал исполнять *другую* программу, нужно семейство `exec`. `exec` не создаёт нового процесса — он берёт текущий и замещает его образ: старый код, данные и стек выбрасываются, на их место загружается новая программа и начинает выполняться со своей `main`. Процесс остаётся тем же самым (тот же pid, те же открытые файлы), но внутри него теперь живёт совсем другая программа.

Отсюда — ключевая особенность, которую надо прочувствовать: при успехе `exec` **не возвращается**. Возвращаться некуда — код, который стоял после вызова, уже затёрт новой программой. Поэтому строка сразу за `exec` исполняется в одном-единственном случае — если запустить программу *не удалось* (нет такого файла, нет прав). По этой причине проверку ошибки ставят первой же строкой после вызова: сам факт, что управление туда дошло, и есть признак провала.

Варианты (`execl`, `execv`, `execlp`, `execvp`, …) отличаются лишь тем, как передавать аргументы. На практике удобнее всего `execvp`: он принимает аргументы массивом и ищет программу по `PATH`, как это делает оболочка. Массив аргументов обязан заканчиваться `NULL`, а нулевым элементом по соглашению идёт имя самой программы.

Ценность `exec` раскрывается именно в паре с `fork`: форкнуться, чтобы получить новый процесс, и тут же вызвать `exec` в потомке, чтобы он стал другой программой, — пока родитель продолжает свою. Это фундаментальный паттерн Unix, на нём стоят и оболочка, и `system()`, и любой запуск подпроцесса.

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                       // потомок станет другой программой
        char *args[] = { "ls", "-l", NULL };
        execvp("ls", args);
        perror("execvp");                 // сюда — только если запуск не удался
        exit(127);
    }
    wait(NULL);                           // родитель дожидается потомка
    printf("parent: child exit\n");
    return 0;
}
```

## pipe: канал между процессами

`fork` даёт два процесса, но с раздельной памятью — просто так они данными не обменяются. Простейший механизм связи — канал (pipe): труба в ядре ОС, у которой два конца. Вызов `pipe(fd)` заполняет массив из двух файловых дескрипторов: `fd[0]` — конец для чтения, `fd[1]` — конец для записи. Всё, что записано в конец записи, выходит из конца чтения в том же порядке (FIFO). Канал однонаправленный: если нужен обмен в обе стороны, заводят два канала — по одному на каждое направление.

Сам по себе, внутри одного процесса, канал бесполезен. Смысл появляется в связке с `fork`: при форке потомок наследует все открытые дескрипторы родителя, поэтому канал, созданный до `fork`, оказывается общим — один процесс пишет в свой конец, другой читает из своего. Так между процессами протягивается провод.

Два прикладных момента, без которых канал ведёт себя загадочно. Во-первых, `read` на пустом канале блокируется — процесс стоит и ждёт, пока данные появятся; это заодно даёт бесплатную синхронизацию (получатель сам собой ждёт отправителя). Во-вторых, каждая сторона должна закрыть тот конец, которым не пользуется. Это не формальность, а условие корректности: `read` возвращает признак конца данных (`0`) только когда закрыты *все* концы записи. Если читатель забыл закрыть свой собственный конец записи, этот конец остаётся открытым — и `read` будет ждать вечно, потому что теоретически «кто-то ещё может написать».

```c
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    pipe(fd);                              // fd[0] — чтение, fd[1] — запись

    if (fork() == 0) {                     
        close(fd[1]);                      
        char buf[64];
        ssize_t n = read(fd[0], buf, sizeof buf);   
        printf("child get: %.*s\n", (int)n, buf);
        close(fd[0]);
        exit(0);
    }

    close(fd[0]);                         
    write(fd[1], "Hello MPSU!", strlen("Hello MPSU!"));
    close(fd[1]);                          
    wait(NULL);
    return 0;
}
```

Родственник pipe — именованный канал, `mkfifo`: та же труба, но с именем в файловой системе, за которое могут ухватиться два *никак не связанных* процесса (обычный pipe наследуется только через родство). Идея та же, поэтому отдельно её не рассматриваем - встретитесь в следующем семестре на курсе по Raspberry у Д.В. :).

## Потоки POSIX

### Что меняется по сравнению с процессами

`fork` создавал новый процесс с отдельной памятью — и оттуда возникли проблемы с общением между родителем и потомком: чтобы обменяться данными, нужен был канал через ядро. Поток устроен противоположно: это ещё одна единица выполнения внутри того же процесса, и память у неё с остальными потоками общая. Глобальная переменная, куча, открытые файлы — всё общее; чтобы один поток передал что-то другому, достаточно записать в переменную, которую видят оба. Своё у каждого потока только то, без чего выполнение невозможно: стек, регистры и точка, в которой он сейчас находится в коде.

Технически поток создается с помощью системного вызова `clone` (тот самый, который вы построите в xv6), но напрямую его почти никто не использует. Работают через библиотеку **POSIX threads** (pthreads): переносимую обёртку над системными вызовами ядра Linux. Поток в ней — это просто функция, которая начинает исполняться параллельно с той, что её запустила.

### pthread_t и pthread_create

Поток представлен значением типа `pthread_t` — это **дескриптор потока** (handle). Заглядывать внутрь него нельзя и не нужно: его роль — быть идентификатором, по которой вы потом обращаетесь к своему потоку (дождаться его, отсоединить). Примерно как pid для процесса, только пользоваться им можно лишь через функции pthreads, а не разбирать как число.

Создаётся поток вызовом `pthread_create`:

```c
int pthread_create(pthread_t *thread,
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *),
                   void *arg);
```

Разберём аргументы вызова. В `thread` указывается дескриптор нового потока —  адрес своей переменной `pthread_t`. `attr` — атрибуты потока (размер стека, политика планирования); в 99% случаев здесь `NULL` — «настройки по умолчанию». `start_routine` — та самая функция, которую поток будет исполнять; её сигнатура жёстко фиксирована: принимает `void *` и возвращает `void *`. И `arg` — единственный аргумент, который этой функции передадут; тоже `void *`.

Поток запускается сразу после вызова функции конкурентно с тем, кто его создал. Дальнейший порядок между ними не определён, ровно как между родителем и потомком после `fork`.

Поток принимает один аргумент типа `void *` и возвращает результат тоже как `void *`. Более подробно разберем эти парамеры ниже

### Как поток завершается: return и pthread_exit

Поток заканчивается тремя способами. Обычный — просто вернуться (`return`) из своей стартовой функции; то, что она вернёт, станет результатом потока. Второй — вызвать `pthread_exit(retval)` откуда угодно, хоть из глубоко вложенной функции: поток немедленно завершится, отдав значение `retval`.

Третий способ более жестокий: если любой поток вызовет `exit()` (или произойдёт возврат из `main`), завершится весь процесс вместе со всеми потоками. Это важное отличие от `pthread_exit`: `exit` убивает всех, `pthread_exit` завершает только текущий поток. (Отсюда трюк: если `main` доходит до конца, но фоновые потоки ещё нужны, `main` вызывает `pthread_exit` вместо `return` — тогда процесс живёт, пока не завершится последний поток. При работе через `join`, который мы сейчас разберём, это почти не встречается.)

### pthread_join и pthread_detach

После создания потока необходимо корректно обработать его завершение. Вариантов два.

`pthread_join(thread, &retval)` — прямой аналог `waitpid`. Он **блокирует** вызывающего, пока указанный поток не завершится, и через `retval` отдаёт тот самый `void *`, что поток вернул. Заодно `join` освобождает ресурсы потока: незавершённая учётная запись потока, которого никто не собрал, — это утечка, тот же зомби, только внутри процесса. Присоединить поток можно один раз.

`pthread_detach(thread)` - эта функция помечает поток отсоединённым: ждать его не нужно и результат забирать не требуется, зато ресурсы освободятся сами в момент завершения. 


### Компиляция

Программе с pthreads нужен ключ `-pthread` — и при компиляции, и при линковке:

```
gcc threads.c -o threads -pthread
```

Он подключает библиотеку потоков и включает нужные для многопоточности определения препроцессора. 

Минимальная программа, собирающая всё вместе:

```c
#include <pthread.h>
#include <stdio.h>

void *worker(void *arg) {
    printf("thread works\n");
    return NULL;
}

int main(void) {
    pthread_t t;
    pthread_create(&t, NULL, worker, NULL);
    pthread_join(t, NULL);               // ждём, результат не нужен → NULL
    printf("main: thread stopped\n");
    return 0;
}
```

### Передача аргументов в поток

Рассмотрим, как возможно передать аргументы в запущенный поток. Приведем два примера - передачи одного значения и нескольких. 

**Одно значение**. Число не требует ни отдельной переменной, ни выделения памяти: его приводят к void *, а в потоке — обратно.

```c
void *worker(void *arg) {
    long id = (long)arg;                 // распаковали обратно
    printf("I am %ld\n", id);
    return NULL;
}
// ...
pthread_create(&t[i], NULL, worker, (void *)i);   // упаковали значение
```

**Несколько значений**. Указатель один, а необходимо передать часть массива на обработку. Значения складывают в структуру и передают указатель на неё. Правило жёсткое: у каждого потока своя структура (массив структур), и она должна жить, пока поток работает, — иначе поток прочитает мусор.

```c
typedef struct {
    int   id;
    long *data;
    int   lo, hi;
} Task;

void *worker(void *arg) {
    Task *t = arg;                       // распаковали структуру
    long sum = 0;
    for (int i = t->lo; i < t->hi; i++)
        sum += t->data[i];
    printf("thread %d: summ = %ld\n", t->id, sum);
    return NULL;
}

int main(void) {
    long data[100];
    // ... заполнить data ...
    pthread_t t[4];
    Task tasks[4];                       // живёт всё время работы потоков
    for (int i = 0; i < 4; i++) {
        tasks[i] = (Task){ .id = i, .data = data,
                           .lo = i * 25, .hi = (i + 1) * 25 };
        pthread_create(&t[i], NULL, worker, &tasks[i]);
    }
    for (int i = 0; i < 4; i++)
        pthread_join(t[i], NULL);
    return 0;
}
```
`tasks[]` лежит в main и переживает все потоки. Передать адрес структуры, которая выйдет из области видимости раньше, чем поток её прочитает, — та же ошибка, что вернуть указатель на локальную переменную: к моменту чтения он уже недействителен.
