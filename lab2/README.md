# Лабораторная работа 2. Синхронизация потоков

В прошлой работе потоки не мешали друг другу: каждый писал в свою ячейку, и `main` собирал результаты только после `join`. В этой работе потоки работают с общими данными одновременно. Рассматриваются ошибки, которые при этом возникают, и средства их предотвращения: мьютексы, условные переменные, семафоры, rwlock и барьеры. Для поиска ошибок используется ThreadSanitizer.

Все примеры из текста лежат полными программами в папке `examples`. Команда `make` собирает их, `make tsan` — их же под ThreadSanitizer (с суффиксом `-tsan`). Запускайте каждый пример по ходу чтения.

## Гонка данных

Возьмём задание 3 из прошлой работы, но пусть четыре потока считают не каждый свою сумму, а одну общую:

```c
#include <pthread.h>
#include <stdio.h>

long count = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        count++;
    return NULL;
}

int main(void) {
    pthread_t t[4];
    for (int i = 0; i < 4; i++)
        pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < 4; i++)
        pthread_join(t[i], NULL);
    printf("count = %ld (ожидалось 4000000)\n", count);
    return 0;
}
```

Пример: `examples/01_race.c`.

```
$ ./01_race
count = 1463707 (ожидалось 4000000)
$ ./01_race
count = 2420098 (ожидалось 4000000)
```

Примеры собираются без оптимизации. С ключом `-O2` компилятор может заменить весь цикл одним сложением, и гонка станет почти незаметной, хотя никуда не денется.

Результат каждый раз другой и всегда меньше ожидаемого. Причина в том, что `count++` — это не одно действие, а три: прочитать значение из памяти в регистр, прибавить единицу, записать обратно. Если два потока одновременно прочитали `100`, оба запишут `101`, и одно увеличение потеряется. Такая ситуация называется **гонкой данных** (data race): два потока обращаются к одной ячейке памяти, хотя бы один из них пишет, и между обращениями нет никакой синхронизации.

Важно отличать гонку данных от более общей **логической гонки** (race condition), когда результат зависит от того, в каком порядке потоки выполнили свои действия. Гонка данных — частный случай, и её умеют находить инструменты. Логическую гонку можно получить и без гонки данных: например, каждое отдельное обращение к данным защищено, а последовательность «проверить, потом изменить» — нет. Её инструмент не увидит, её можно поймать только проверкой результата.

## Мьютекс

Мьютекс (mutex, mutual exclusion — взаимное исключение) — это замок, который в каждый момент может держать только один поток. Поток, вызвавший `pthread_mutex_lock` на занятом мьютексе, засыпает и ждёт, пока владелец не вызовет `pthread_mutex_unlock`. Код между `lock` и `unlock` называется **критической секцией**: в ней одновременно находится не больше одного потока.

```c
long count = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&m);
        count++;
        pthread_mutex_unlock(&m);
    }
    return NULL;
}
```

Теперь программа всегда печатает `4000000` (пример: `examples/02_mutex.c`). Мьютекс, объявленный глобально, инициализируется макросом `PTHREAD_MUTEX_INITIALIZER`; мьютекс в структуре или массиве — вызовом `pthread_mutex_init(&m, NULL)`.

Полезно думать о мьютексе не как о защите кода, а как о защите **данных и их инварианта** — утверждения, которое верно, пока мьютекс никто не держит. Для счётчика инвариант простой: `count` равен числу выполненных увеличений. Внутри критической секции инвариант можно временно нарушать, но к `unlock` он должен быть восстановлен. Отсюда два правила. Мьютекс защищает данные, только если **все** обращения к ним идут под ним: один забытый `lock` в одной функции — и защиты нет. И критическая секция должна охватывать всю операцию целиком, а не каждое обращение по отдельности.

Если потоку нужно несколько мьютексов сразу, появляется опасность взаимной блокировки (deadlock): первый поток держит A и ждёт B, второй держит B и ждёт A, и оба ждут вечно. Подробно мы разбирали это на семинаре; главное лекарство — договориться, что все потоки захватывают мьютексы в одном и том же порядке.

## Условная переменная

Мьютекс решает задачу «не мешать друг другу», но не задачу «дождаться». Пусть поток должен ждать, пока другой поток не подготовит данные. Можно в цикле проверять флаг, но такое активное ожидание впустую сжигает процессор, а проверять флаг без мьютекса — это снова гонка данных.

Для ожидания существует **условная переменная** `pthread_cond_t`. Она всегда работает в паре с мьютексом, который защищает само условие:

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;
int ready = 0;

/* поток, который ждёт */
pthread_mutex_lock(&m);
while (!ready)
    pthread_cond_wait(&c, &m);
/* здесь ready == 1, и мьютекс снова у нас */
pthread_mutex_unlock(&m);

/* поток, который сообщает */
pthread_mutex_lock(&m);
ready = 1;
pthread_cond_signal(&c);
pthread_mutex_unlock(&m);
```

Полная программа — `examples/03_condvar.c`. В ней `main` две секунды готовит данные, а второй поток всё это время спит и процессор не занимает. Убедиться в этом можно командой `top -H` в соседнем терминале.

Главное происходит внутри `pthread_cond_wait(&c, &m)`: он **атомарно** отпускает мьютекс и усыпляет поток, а после пробуждения снова захватывает мьютекс и только потом возвращается. Атомарность здесь принципиальна: если бы поток сначала отпустил мьютекс, а потом заснул, сигнал мог бы прийти ровно между этими действиями и потеряться.

Ожидание всегда пишется в цикле `while`, а не в `if`. Во-первых, допускаются ложные пробуждения: `pthread_cond_wait` может вернуться, хотя сигнала не было. Во-вторых, пока разбуженный поток снова захватывал мьютекс, другой поток мог успеть «съесть» то, чего он ждал. После пробуждения условие нужно проверить заново.

`pthread_cond_signal` будит один ждущий поток, `pthread_cond_broadcast` — все. Если ждущие потоки ждут разного (одни — места, другие — данных), удобнее завести две условные переменные, чтобы будить только тех, кому есть смысл просыпаться.

## Семафор

Семафор — это счётчик, который не может стать отрицательным. `sem_wait` уменьшает его на единицу, а если он равен нулю — ждёт, пока кто-нибудь не увеличит. `sem_post` увеличивает счётчик и будит одного ждущего. Семафоры POSIX объявлены в `<semaphore.h>`:

```c
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, 3);    /* 0 — общий для потоков одного процесса; 3 — начальное значение */
sem_wait(&s);
/* ... */
sem_post(&s);
```

Семафор используется в двух ролях. Как **счётчик ресурсов**: начальное значение равно числу ресурсов (скажем, трём свободным соединениям с базой), каждый поток берёт ресурс через `sem_wait` и возвращает через `sem_post`. Как **сигнал о событии**: начальное значение 0, один поток ждёт в `sem_wait`, другой сообщает, что событие произошло, через `sem_post`. В отличие от мьютекса, у семафора нет владельца: `post` может сделать не тот поток, который делал `wait`.

Обе роли показаны в `examples/04_semaphore.c`. Шесть потоков делят три «соединения с базой», и по выводу видно, что одновременно занято не больше трёх. А `main` ждёт завершения потоков без `join`, через второй семафор с начальным значением 0.

## rwlock и барьер

**rwlock** (`pthread_rwlock_t`) — замок с двумя режимами. Захват на чтение (`pthread_rwlock_rdlock`) могут держать сколько угодно потоков одновременно, захват на запись (`pthread_rwlock_wrlock`) — только один, и в это время читателей нет. Освобождение в обоих случаях — `pthread_rwlock_unlock`. rwlock выгоден, когда данные почти только читают. Как мы видели на семинаре на примере LRU-кэша, нужно внимательно проверять, что «чтение» действительно ничего не меняет.

В `examples/05_rwlock.c` пять читателей и один писатель работают с настройками. Программа печатает, сколько читателей было внутри одновременно. Попробуйте два изменения. Первое: замените `rdlock` на `wrlock` у читателей. Второе: уберите паузу между чтениями. Во втором случае программа зависнет: читатели сменяют друг друга без перерыва, и писатель никогда не дождётся момента, когда внутри никого нет. Это называется **голоданием писателя**.

**Барьер** (`pthread_barrier_t`) — точка встречи. Он создаётся на заданное число потоков вызовом `pthread_barrier_init(&b, NULL, n)`. Поток, вызвавший `pthread_barrier_wait(&b)`, засыпает, пока до этого места не дойдут все `n` потоков; после этого все проходят дальше, и барьер готов к следующему использованию. Барьер нужен, когда работа идёт этапами и следующий этап можно начинать, только когда предыдущий завершили все.

В `examples/06_barrier.c` три потока проходят три этапа. Закомментируйте вызов `pthread_barrier_wait` — и сообщения разных этапов перемешаются.

## ThreadSanitizer

Гонки данных проявляются не при каждом запуске, поэтому «у меня сработало» ничего не доказывает. Искать их помогает ThreadSanitizer (TSan) — режим компилятора, при котором каждое обращение к памяти и каждая операция синхронизации записываются, а затем проверяются на гонки. Программу нужно собрать с ключом `-fsanitize=thread`:

```
gcc -g -fsanitize=thread 01_race.c -o 01_race-tsan -pthread
./01_race-tsan
```

Для программы со счётчиком без мьютекса TSan печатает:

```
WARNING: ThreadSanitizer: data race (pid=609)
  Write of size 8 at 0x55fe3cb9b018 by thread T2:
    #0 worker 01_race.c:17

  Previous read of size 8 at 0x55fe3cb9b018 by thread T1:
    #0 worker 01_race.c:17

  Location is global 'count' of size 8 at 0x55fe3cb9b018
```

Отчёт говорит, какая переменная (`count`), какие два обращения конфликтуют (запись в потоке T2 и чтение в T1) и в какой строке они находятся. Ключ `-g` нужен, чтобы в отчёте были номера строк. Программа под TSan работает в несколько раз медленнее и потребляет больше памяти, поэтому для обычной работы её собирают без этого ключа.

Что TSan находит: гонки данных и нарушение порядка захвата мьютексов (`lock-order-inversion`) — ситуацию, когда в одном месте берут A, потом B, а в другом B, потом A. Что TSan не находит: логические гонки без гонки данных, а также deadlock, который уже случился. Если программа зависла, TSan ничего не напишет: подключитесь к процессу отладчиком командой `gdb -p <pid>` и посмотрите, где стоит каждый поток (`thread apply all bt`).

Если TSan сразу падает с сообщением `FATAL: ThreadSanitizer: unexpected memory mapping`, это несовместимость со свежими ядрами Linux. Лечится командой `sudo sysctl vm.mmap_rnd_bits=28`.

## Под капотом

Все примитивы этой работы в Linux построены на одном системном вызове — `futex`. Пока мьютекс свободен, `pthread_mutex_lock` захватывает его одной атомарной инструкцией в пользовательском пространстве, не обращаясь к ядру. Только если мьютекс занят, поток просит ядро усыпить его вызовом `futex(FUTEX_WAIT)`, а освобождающий поток будит его вызовом `futex(FUTEX_WAKE)`. Это видно, если запустить пример с мьютексом под `strace -f -e trace=futex ./02_mutex`: на миллионы захватов мьютекса приходятся лишь сотни вызовов `futex`. Этот системный вызов, а поверх него мьютекс и условную переменную, вы построите сами в xv6.

# Практикум

Каждая задача — готовая программа, которая правильно работает в одном потоке и ломается в нескольких. Синхронизации в ней нет, места для неё помечены `TODO`. В конце `main` проверяет результат и печатает «корректно» или «НЕКОРРЕКТНО»; если программа не уложилась в 10 секунд, она сообщает, что зависла. Кроме правильности результата, `main` проверяет, что синхронизация не уничтожила смысл многопоточности: решение, в котором потоки на деле работают строго по очереди или ждут, впустую занимая процессор, тоже считается некорректным. Проверку в `main` и вспомогательные функции, помеченные «не трогайте», менять нельзя.

Какой примитив использовать, решаете вы сами. Задача считается сданной, если выполнены все условия:

1. Программа печатает «корректно» десять запусков подряд:
   ```
   for i in $(seq 10); do ./bank | tail -1; done
   ```
2. Версия, собранная с `-fsanitize=thread`, не выдаёт ни одного предупреждения.
3. Вы можете объяснить, почему выбрали именно этот примитив и что сломается, если убрать или переставить любую из добавленных строк.

## Задание 1. Переводы между счетами (`bank.c`)

**Задача.** Четыре потока делают случайные переводы между десятью счетами функцией `transfer(from, to, amount)`. В конце сумма по всем счетам должна остаться прежней, а отрицательных балансов быть не должно. Добавьте синхронизацию в `transfer`.

Внутри перевода вызывается функция `audit()`: она изображает проверку операции банком и заодно считает, сколько переводов выполнялось одновременно. Переводы между разными парами счетов (например, 1→2 и 5→7) должны идти параллельно. Если переводы шли строго по одному — например, под одним мьютексом на весь банк, — программа напишет, что параллельности нет, и решение не засчитывается. Если программа зависла, вспомните семинар.

## Задание 2. Ограниченный буфер (`buffer.c`)

**Задача.** Три производителя кладут числа в общий буфер на 8 ячеек функцией `put`, два потребителя забирают их функцией `get`. Если буфер полон, `put` должен ждать; если пуст — ждать должен `get`. Каждое число должно быть потреблено ровно один раз. Добавьте синхронизацию в `put` и `get`.

В выданном коде ожидание сделано циклом с `sched_yield()`. В решении активного ожидания быть не должно: ждущий поток должен спать, а не крутиться в цикле. Это проверяется: производители работают медленно, поэтому потребители почти всё время ждут, и `main` сравнивает процессорное время программы с реальным. Если процессор был занят больше половины реального времени, значит, потоки ждали, крутясь в цикле, и решение не засчитывается.

## Задание 3. Игра «Жизнь» (`life.c`)

**Задача.** Поле 512×512 обновляется 300 шагов, каждый из четырёх потоков считает свою полосу строк. Чтобы посчитать свою полосу, потоку нужны и соседние строки чужих полос. `main` сравнивает результат с однопоточным эталоном. Добавьте синхронизацию в `worker`.

`main` также печатает, во сколько раз многопоточный расчёт быстрее однопоточного. Ускорение должно быть заметно больше единицы; сколько именно можно получить, зависит от числа ядер вашей машины (команда `nproc`). Если ускорения нет, объясните на защите, почему.
