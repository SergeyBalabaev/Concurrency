## Пул и future

Завести по потоку на каждое дело — плохая идея: тысяча задач превращается в тысячу потоков, у каждого свой стек и своя запись в планировщике ядра. Пул поступает иначе: заранее создаёт несколько рабочих потоков и складывает задачи в очередь, а освободившийся рабочий берёт из неё следующую.

Отдав задачу в пул, мы получаем **future** — обещание результата: «он будет здесь, когда задача выполнится». В `concurrent.futures` для этого есть:

- `ThreadPoolExecutor` — пул потоков;
- `ProcessPoolExecutor` — пул процессов с тем же интерфейсом;
- `Future` — то, что возвращает `submit`.

`submit(fn, *args)` кладёт вызов в очередь и сразу возвращает `Future`; `map(fn, iterable)` делает то же для набора аргументов и отдаёт результаты в исходном порядке. Пул обычно создают через `with`: на выходе из блока он **дожидается всех отправленных задач** и останавливает рабочих.

Пусть нужно «скачать» 10 файлов по полсекунды каждый. Последовательно — 5 секунд, хотя почти всё это время программа просто ждёт:

```python
import time
from concurrent.futures import ThreadPoolExecutor

def download(n):
    time.sleep(0.5)                       # «ждём сеть»
    return f"файл {n}"

with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(download, range(10)))   # 0.5 с вместо 5
```

Пример целиком, с последовательным вариантом для сравнения, — `examples/io_seq_vs_pool.py`.

Сколько потоков ставить в пул? Для задач, которые ждут сеть, ограничивает не число ядер, а то, сколько одновременных запросов готова обслужить другая сторона. `examples/max_workers.py` скачивает 40 элементов с локального сервера, который обслуживает не больше 8 запросов одновременно: время падает почти пропорционально, пока потоков меньше восьми, а дальше выходит на плато. Хорошее значение `max_workers` находится измерением, а не угадыванием.

## GIL: когда потоки помогают, а когда нет

В CPython есть глобальная блокировка интерпретатора — **GIL**. Это мьютекс, который поток обязан держать, чтобы исполнять байткод Python, поэтому в каждый момент Python-код выполняет только **один** поток процесса, сколько бы ядер ни было. Но на время блокирующих операций — `time.sleep`, чтения из сокета или файла — GIL отпускается, и другой поток спокойно работает.

Отсюда правило, на котором держится вся работа:

- **IO-bound** задачи (программа в основном ждёт сеть, диск, другой процесс) хорошо ускоряются потоками;
- **CPU-bound** задачи (программа в основном считает на чистом Python) потоками не ускоряются — нужны процессы, у каждого из которых свой интерпретатор и свой GIL.

Благодаря одинаковому интерфейсу пулы различаются только классом:

```python
def with_pool(executor_class):
    with executor_class(max_workers=4) as pool:
        futures = [pool.submit(count_primes, lo, hi) for lo, hi in ranges()]
        return sum(f.result() for f in futures)

if __name__ == "__main__":                # обязательно для ProcessPoolExecutor!
    measure("4 потока", with_pool, ThreadPoolExecutor)
    measure("4 процесса", with_pool, ProcessPoolExecutor)
```

```
ядер: 2
один поток  : 78498 простых, 3.25 с
4 потока    : 78498 простых, 3.28 с
4 процесса  : 78498 простых, 1.71 с
```

Это `examples/cpu_threads_vs_procs.py`. Потоки не дали ничего, процессы ускорили примерно во столько раз, сколько ядер доступно.

У процессов своя память (вспомните `fork` из ЛР1), и за это приходится платить. Функция, её аргументы и результат пересылаются между процессами через сериализацию (`pickle`), поэтому процессам нужно давать **крупные** куски работы и передавать **мало** данных. Функция должна быть объявлена на верхнем уровне модуля (лямбду переслать нельзя), а запуск пула — стоять под `if __name__ == "__main__":`, иначе каждый дочерний процесс при импорте модуля снова начнёт создавать пул.

## Результат и ошибки

У `Future` два главных метода:

- `result(timeout=None)` — дождаться и вернуть результат; если задача упала, `result()` **выбрасывает то же исключение** в вызывающем потоке;
- `done()` — готова ли задача, без ожидания.

Важное следствие: исключение внутри задачи в пуле не печатается и не роняет программу. Оно тихо лежит в `Future`, пока кто-нибудь не вызовет `result()`. Если результат никто не забрал, ошибка теряется:

```python
with ThreadPoolExecutor(max_workers=4) as pool:
    pool.submit(task, 3)                  # Future выбросили — ошибку никто не увидит

with ThreadPoolExecutor(max_workers=4) as pool:
    f = pool.submit(task, 3)
    try:
        print(f.result())
    except ValueError as e:
        print("ошибка:", e)
```

Сравните оба варианта в `examples/future_errors.py`.

## Ожидание группы: All и FirstOf

`map` отдаёт результаты в порядке подачи, поэтому ждёт самую медленную задачу, даже если остальные давно готовы. Чтобы получать результаты **по мере готовности**, есть `as_completed(futures)` — итератор, который выдаёт future в том порядке, в каком они завершаются. Чтобы понять, какой future к какой задаче относится, их удобно складывать в словарь:

```python
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = {pool.submit(work, n): n for n in range(4)}   # Future -> номер задачи
    for f in as_completed(futures):
        print(f"задача {futures[f]} готова: {f.result()}")
```

В `examples/as_completed_demo.py` самая медленная задача идёт первой: с `map` все результаты появляются разом через 2 с, с `as_completed` быстрые печатаются сразу.

Функция `wait(futures, timeout=None, return_when=...)` ждёт группу future и возвращает пару множеств `(done, not_done)`. Параметр `return_when` и даёт комбинаторы с лекции:

- `ALL_COMPLETED` (по умолчанию) — **All**: вернуться, когда готовы все;
- `FIRST_COMPLETED` — **FirstOf**: вернуться, как только готов хоть один.

```python
with ThreadPoolExecutor() as pool:
    futures = [pool.submit(download_from, m) for m in MIRRORS]
    done, not_done = wait(futures, return_when=FIRST_COMPLETED)
    print("победитель:", done.pop().result())
# выход из with ждёт и остальные задачи!
```

В `examples/wait_first.py` ответ самого быстрого зеркала приходит через 0.4 с, а из блока `with` программа выходит только через 1.5 с: «проигравших» никто не остановил, и пул честно их дожидается.

Есть и третий способ — повесить на future колбэк: `f.add_done_callback(fn)` вызовет `fn(f)`, когда задача завершится. Это аналог Subscribe с лекции, и, как на лекции, колбэк вызывает тот, кто «пришёл вторым»: рабочий поток, завершивший задачу, или сразу текущий поток, если future уже готов (`examples/done_callback.py`).

## Отмена

`f.cancel()` отменяет задачу, **только если она ещё не начала выполняться** и ждёт в очереди. Прервать функцию, которая уже исполняется в потоке, Python не умеет. Похожая ловушка с таймаутом: `f.result(timeout=0.3)` выбрасывает `TimeoutError`, но сама задача продолжает работать — перестали ждать мы, а не она. Оба эффекта видны в `examples/cancel_demo.py`.

Раз остановить поток снаружи нельзя, остаётся **попросить** его остановиться — кооперативная отмена с лекции. Роль стоп-токена играет `threading.Event`: один поток взводит флаг методом `set()`, рабочие проверяют его через `is_set()`. Ждать удобнее не через `time.sleep(t)`, а через `stop.wait(t)`: это тот же сон, но он прерывается сразу, как только кто-то вызовет `set()`.

```python
def worker(name, stop):
    for step in range(10):
        if stop.is_set():
            print(f"{name}: стоп на шаге {step}")
            return
        stop.wait(0.5)                    # как sleep, но просыпается сразу при set()
```

В `examples/cancel_event.py` сравните рабочего, который проверяет флаг, и рабочего, который просто спит: первый останавливается мгновенно, второго приходится ждать до конца.
